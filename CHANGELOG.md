## Unreleased

### Breaking Changes

Timeout handling was reworked. A request timeout is now a thing of its own, separate from the transport timeouts, and it no longer takes the connection down with it. See the README section on timeouts for the new model.

* A slow query now raises `Cassandra\Exception\RequestTimeoutException` instead of a transport `SocketException`/`StreamException`. Note it is deliberately *not* a `NodeException`: nothing is wrong with the node, so `catch (NodeException)` no longer covers this case.
* These now return `null` when the given timeout elapses:
    * `Cassandra\Connection::waitForNextEvent(): ?Cassandra\Response\Event`
    * `Cassandra\Connection::waitForNextResponse(): ?Cassandra\Response\Response`
    * `Cassandra\Connection::waitForAnyStatement(): ?Cassandra\Statement`
* Default timeouts changed: receive 15s (was 10s socket / 30s stream), socket send 10s (was 5s), and every request now has a 30s request timeout on top.
* A transport timeout of zero now means "no timeout" instead of being raised to one second — `['sec' => 0, 'usec' => 0]` for `SO_RCVTIMEO`/`SO_SNDTIMEO`, `timeoutInSeconds: 0` for `StreamNodeConfig`.
* `Cassandra\Connection::getResponseForStatement()` now raises a server error instead of returning the `Cassandra\Response\Error` frame, matching `syncRequest()` and `Cassandra\Statement::getResponse()` — and matching what it already did for a statement that was answered before the call. The frame-level reads are unchanged: `waitForNextResponse()` and `tryReadNextResponse()` still hand error frames back, since they were asked for whatever comes next rather than about a request of yours.
* `Cassandra\Request\Request::getStream()` and `Cassandra\Protocol\Frame::getStream()` return `?int`: a request has no stream id until it is sent, and encoding one without an id throws. Only affects code that builds frames by hand — `Connection` assigns an id before every write.
* `Cassandra\Connection\ConnectionOptions` now rejects a non-positive `requestTimeoutInSeconds`, `heartbeatIntervalInSeconds` or `heartbeatTimeoutInSeconds` with a `Cassandra\Exception\ConnectionException`. Each of them meant something no caller can have wanted — a request out of time before it was sent, a probe on every single read, or a heartbeat overdue the moment it went out, which declared every healthy node dead. "No timeout" is spelled `null` for the two that allow it.
* A non-positive request timeout is now rejected wherever one can be given, not only in `ConnectionOptions`: `QueryOptions`, `ExecuteOptions`, `BatchOptions` and `PrepareOptions` raise a `Cassandra\Exception\RequestException` from their constructor, and `Cassandra\Connection::setRequestTimeout()` and the per-call `$requestTimeoutInSeconds` argument raise a `Cassandra\Exception\ConnectionException`. Previously the value was normalised to zero and silently expired every request it applied to — which through `setRequestTimeout()` includes the ones already in flight, and enough of those at once replaces the connection through `maxOrphanedStreams`. "Fall back to the next level" is spelled `null` everywhere.
* `Cassandra\Connection\Node::readAvailableData()` was removed, along with its implementation in `Cassandra\Connection\NodeImplementation`. `Cassandra\Response\ProgressiveStreamReader` was its only caller and is gone; response bodies are read with `read()`, which is exact rather than best-effort. Only affects code that implements the transport interface.
* `Cassandra\Response\ProgressiveStreamReader` was removed, along with its exception codes `RESPONSE_PSR_GET_DATA_NOT_SUPPORTED` and `RESPONSE_PSR_SOURCE_NOT_SET`. Inherited from the upstream driver and unreachable here: nothing ever constructed one or called `setSource()`, so there was no way to obtain one from a response. It cannot be revived either — response bodies are read whole before a response is built, and with v5 framing and multiplexed stream ids, pulling more bytes from the node while parsing one response would consume another request's frames.
* `Cassandra\Response\StreamReader` is now `final`, since the reader above was the only thing that ever extended it.
* On protocol v5, a request sent with `syncRequest()`/`asyncRequest()` now runs against the connection's keyspace instead of none. The keyspace is filled into every request on its way to the wire, not only into the ones `Connection` builds, so a hand-built `Query`/`Execute`/`Prepare`/`Batch` behaves like `query()` and friends. A request that names a keyspace of its own is left alone; to send one deliberately without a keyspace on a connection that has one, qualify the table name. A request sent more than once takes whatever the connection is on at each send — only a keyspace the caller put on the request survives a later `setKeyspace()`. `Cassandra\Request\Request::applyDefaultKeyspace()` is the hook, overridden by the four request types that carry options; an override decides with `acceptsDefaultKeyspace()` and records with `markKeyspaceAsConnectionDefault()`, rather than testing the keyspace option for null, which cannot tell a caller's keyspace from one an earlier send left behind. Only relevant to code that implements its own request type.
* `Cassandra\Connection::setKeyspace()` now sends the keyspace as a quoted identifier, so the name is taken exactly as given on every protocol version. Up to v4 the unquoted `USE` was folded to lower case by the server, while from v5 the keyspace request option was not — the same connection, addressed the same way, ended up on two different keyspaces. Code that relied on the folding must now pass the name exactly as it exists server-side, which for a keyspace created with an unquoted identifier is the lower-cased form: a keyspace created as `CREATE KEYSPACE MyKs` is `myks`, and `setKeyspace('MyKs')` now fails where it used to work. It also closes a CQL injection: a keyspace name containing a semicolon carried whatever followed it into the statement.
* `Cassandra\Connection::setKeyspace('')` now raises a `Cassandra\Exception\ConnectionException` (`CONNECTION_KEYSPACE_CANNOT_BE_CLEARED`) on a *connected* v3/v4 connection that is on a keyspace. Up to v4 the keyspace belongs to the node's session and there is no CQL that un-sets one, so the call was silently recording a keyspace the requests did not actually run against: every unqualified request kept going to the previous keyspace while `getKeyspace()` named none. Before connecting, from v5, and where there was no keyspace to begin with, it is recorded as before. To move a connected v3/v4 connection off its keyspace, `disconnect()` first: with no connection there is no node session to contradict, so an empty keyspace is then recorded like any other value and the next connect opens on none. Disconnecting alone does not clear it — what the connection is on outlives the socket, which is why reconnecting sends the `USE` again.
* Every `waitFor…()` method now rejects a `NAN` `$timeoutInSeconds` with a `Cassandra\Exception\ConnectionException` (`CONNECTION_INVALID_WAIT_TIMEOUT`): `waitForNextEvent()`, `waitForNextResponse()`, `waitForStatements()`, `waitForAnyStatement()` and `waitForAllPendingStatements()`. `NAN` passes every comparison rather than failing them, so it produced a deadline no clock ever reaches *and* a read that was never allowed to block — an endless wait that spun at full CPU instead of waiting. Zero, negative and `INF` values are unaffected. The request-timeout arguments already refused `NAN` by requiring a value greater than zero.
* `Cassandra\Connection\Node::read()`, `readAvailableData()` and `readAvailableDataFromSource()` take `?float $readDeadline` — an absolute microtime — in place of `bool $waitForData`. `null` keeps the old "block for as long as the transport allows" behaviour and `Node::DO_NOT_WAIT` the old `false`. Only affects code that implements the transport interfaces; the bundled `Socket`, `Stream`, `FrameCodec` and `RequestCompressor` are all updated.
* `Cassandra\Connection\Node` gained `getReceivedByteCount(): int`, a monotonically rising count of the bytes taken off the connection. It is the only evidence of a live connection that does not depend on a whole frame having arrived, which is what the heartbeat needs to avoid dropping a connection mid-transfer (see Fixed). `Cassandra\Connection\NodeImplementation` implements it for every transport built on it, so only a transport written against the interface directly has anything to add; a decorator must report the count of the node it wraps rather than of what it hands on.
* A `timeuuid` value is now checked to be a version 1 UUID on every read path, not only on some of them. `Cassandra\Response\StreamReader` decodes `uuid` and `timeuuid` cells without building a value object — the path every cell of a result row comes through, a bare column and the elements of a list, set, map, tuple or UDT alike — while a vector element and `Cassandra\Value\Timeuuid::fromBinary()` go through `Cassandra\Value\Timeuuid`, which has always refused anything else. The same bytes therefore decoded in one place and raised in the other, and a value read with `UuidEncodeOption::AS_BINARY` could not always be handed back to `Timeuuid::fromValue()`. Reading a non-version-1 value out of a `timeuuid` column now raises `Cassandra\Exception\ValueException` (`VALUE_TIMEUUID_INVALID_VERSION`) wherever it appears. Cassandra enforces the version on write, so this is data no node produces; `uuid` columns are unaffected and still take any 16 bytes.
* `Cassandra\Connection` now rejects an empty node list with a `Cassandra\Exception\ConnectionException` (`CONNECTION_NO_NODES_CONFIGURED`). The list is fixed for the life of the object, so nothing the caller does later could make such a connection work; it used to be accepted and then surface several calls on as "unable to connect to any Cassandra node", which reads like an unreachable cluster rather than a connection that was never given one.
* `Cassandra\Value\Varint` now rejects a magnitude of more than 4096 decimal digits (`VALUE_VARINT_MAGNITUDE_TOO_LARGE`), and `Cassandra\Value\Decimal` an unscaled part of the same width (`VALUE_DECIMAL_UNSCALED_TOO_LARGE`). Converting between a varint's wire form and its decimal spelling is quadratic in the length of the value on the pure-PHP calculator — the fallback a build without `gmp` and without `bcmath` uses — so an unbounded magnitude was not merely slow but a decode-side denial of service: the cell length is the peer's to choose and is bounded only by the frame, and eight kilobytes of it cost half a minute of CPU. The bound is the time counterpart of `Decimal`'s existing scale bound, which caps memory; the two are orthogonal, so `1e-100000` (a huge scale over an unscaled part of 1) is still accepted while `1e100000` is not. 4096 digits is some 13,600 bits — wider than any key, hash or identifier a column holds — so no real value reaches it. It is applied on both sides, so nothing is written that could not be read back.
* `Cassandra\Value\Time::asDateTime()` returns its `DateTimeImmutable` in UTC rather than in the ambient default timezone. Code that read the wall clock off it (`format('H:i:s')`, `->format('u')`) is unaffected — the time of day is unchanged, and it always round-tripped back through `new Time($dateTime)`. Code that read the *offset*, compared the object against one built elsewhere, or formatted it with `P`/`T`/`U` now sees UTC. This makes the three temporal types agree: `Date` and `Timestamp` already returned UTC.
* `Cassandra\Connection\ConnectionOptions` now rejects a negative `preparedResultCacheSize` or `maxOrphanedStreams` with a `Cassandra\Exception\ConnectionException`. Both were clamped by the code that reads them, so a negative value did not misbehave — it quietly became something else entirely: a disabled prepared-statement cache, or a connection that replaces itself as soon as one stream id is held back. Zero remains a legitimate setting for either and means exactly those two things deliberately.
* `Cassandra\Value\Timestamp` reads a string that names no UTC offset as UTC rather than in the ambient `date_default_timezone_set()` zone. Code that relied on the old reading — a zoneless literal meaning local wall-clock time — must now say the offset it means, which `Timestamp` has always accepted (`'2024-01-01T12:00:00+02:00'`), or pass a `DateTimeInterface` built in that zone. See Fixed.
* `Cassandra\Value\Inet` validates its address at construction instead of at `getBinary()`, so `Inet::fromValue()` and `Inet::fromMixedValue()` raise a `Cassandra\Exception\ValueException` for one that is not an IPv4 or IPv6 address.
* `Cassandra\Response\Error\Context\ReadFailureContext::$dataPresent` is a `bool`, matching `ReadTimeoutContext::$dataPresent` and the flag the protocol actually carries; it used to hand back the raw byte as an `int`. `toArray()` reports `data_present` as a bool for the same reason.
* `Cassandra\Connection\Node::read()` and `readAvailableDataFromSource()` document `Cassandra\Exception\CompressionException` alongside `NodeException`. From v5 the framing is a transport concern, so a read genuinely decompresses and can refuse a payload — `Cassandra\Connection\FrameCodec` already threw one, the interface simply did not say so. Only affects code that implements or calls the transport interface directly; the bundled transports are unchanged.

### Added
* Map decoding can now represent every legal CQL key shape. `ValueEncodeConfig(mapEncodeOption: MapEncodeOption::AUTO)` is the default: maps whose configured keys fit losslessly in PHP's `int|string` array-key model remain native arrays, while object and composite keys return a `Cassandra\Value\MapCollection` containing ordered `MapEntry` objects. `AS_MAP_COLLECTION` forces that representation and `AS_ARRAY` requires the legacy array form, raising `VALUE_MAP_CANNOT_CONVERT_TO_ARRAY` rather than stringifying or collapsing keys. `MapCollection::fromEntries()` provides the corresponding write path for tuple, frozen UDT and other non-array-key values.
* `Cassandra\Value\EncodeOption\UuidEncodeOption`: `uuid`/`timeuuid` values can now be decoded either as the canonical 36-character string (`AS_STRING`, the default) or as the raw 16-byte binary form (`AS_BINARY`), selected via `ValueEncodeConfig(uuidEncodeOption: …)`. The binary form skips the hex-formatting step entirely, which is worth it when reading large result sets keyed by UUID; the string form remains the default for ergonomics.
* `Cassandra\Value\Uuid` / `Cassandra\Value\Timeuuid`: the constructor now also accepts the raw 16-byte binary form in addition to the canonical string, so a value read with `UuidEncodeOption::AS_BINARY` can be re-bound directly without a format→parse round-trip. The value is stored raw internally, making `getBinary()` a no-op and normalizing `getValue()` to the canonical lowercase string. The two forms are distinguished by length and cannot collide (a canonical string is always 36 characters).
* `Cassandra\Compression\Lz4Compressor`: a pure-PHP LZ4 block compressor. When compression is negotiated, outgoing request frames are now compressed as well as incoming responses — previously only responses were decompressed and requests were always sent uncompressed.
* Optional native LZ4 acceleration: when the `lz4` PHP extension is installed it is used automatically for block (de)compression (much faster), with the pure-PHP implementation as a transparent fallback.
* Request timeouts: `Cassandra\Connection\ConnectionOptions::$requestTimeoutInSeconds` (default 30s) bounds how long the server may take to answer, raising the new `Cassandra\Exception\RequestTimeoutException`. Set it per request via `requestTimeoutInSeconds` on `QueryOptions`/`ExecuteOptions`/`BatchOptions`/`PrepareOptions`, for everything that follows via `Cassandra\Connection::setRequestTimeout()`, or for a single call via the `$requestTimeoutInSeconds` argument. The most specific one wins.
* A `$requestTimeoutInSeconds` argument on every call that sends a request, so a single call can be given its own budget without going through request options: `syncRequest()`, `asyncRequest()`, `query()`, `queryAll()`, `queryAsync()`, `execute()`, `executeAll()`, `executeAsync()`, `batch()`, `batchAsync()`, `prepare()` and `prepareAsync()`. It is the last parameter of each, so existing positional calls are unaffected. On the paged helpers (`queryAll()`, `executeAll()`) it bounds each page request rather than the call as a whole.
* `Cassandra\Exception\RequestTimeoutException::getTimedOutStatements()`: the statements that ran out of time, ready to be sent again.
* Wait bounds: every `waitFor…()` method takes `$timeoutInSeconds` limiting how long that call blocks — `0` makes one non-blocking read attempt and returns, `INF` waits indefinitely, `null` uses the method's own default. A wait never blocks on the transport once its deadline has passed, so a bound of `0` and a request that has already run out are both reported at once rather than after another receive timeout.
* `Cassandra\Statement::isTimedOut()` and `Cassandra\Statement::isAbandoned()` (with `Cassandra\StatementStatus::TIMED_OUT` / `ABANDONED`): why a statement can no longer be resolved — it ran out of time, or it was given up on because the connection was closed under it or a follow-up request of its own (a repreparation, an auto-prepared execute) never reached the node. Either way, send the request again.
* `Cassandra\Connection\ConnectionOptions::$maxOrphanedStreams` (default 24): how many timed-out requests a connection may accumulate before it is replaced with a fresh one, raising a `Cassandra\Exception\ConnectionException`.
* Connection heartbeat: `Cassandra\Connection\ConnectionOptions::$heartbeatIntervalInSeconds` / `$heartbeatTimeoutInSeconds` (defaults 30s / 5s). A connection that has gone quiet is probed with an OPTIONS request, so one that died is noticed after roughly interval + timeout — while waiting for events, or while waiting for a slow answer — instead of looking like a server that is merely thinking. The probe is the driver's own request and stays out of the caller's way: its answer is resolved out of sight rather than handed back by `waitForNextResponse()`/`tryReadNextResponse()`, it is not held to your request timeout, and it does not keep `waitForAllPendingStatements()` waiting.
* `Cassandra\Connection\SocketNodeConfig::$connectTimeoutInSeconds` (default 5s): the socket transport now has its own connect timeout instead of borrowing `SO_SNDTIMEO`, so tuning the write timeout no longer silently changes how long connecting may take. It must be greater than zero.
* Sub-second timeouts: every transport timeout accepts fractional seconds.
* Smaller additions that come with the above: `Cassandra\Request\Request::getRequestTimeout()`, `Cassandra\Request\Batch::getOptions()`, `Cassandra\Statement::getRequestTimeout()` / `getSentAt()` and `Cassandra\Exception\NodeException::isReadTimeout()`.
* `Cassandra\Connection::getKeyspace()`: the keyspace the connection's requests run against, so a request built by hand can be given the same one.
* `Cassandra\Statement::peekResponse()`: the answer if it has already arrived, and `null` otherwise. Unlike `getResponse()` and `tryGetResponse()` it only looks — it never reads from the connection and never raises the server's error.
* `Cassandra\Protocol\ProtocolVersion::PREFERRED_ORDER` replaces the misspelled `PREFRED_ORDER`, which is kept as a deprecated alias of it so existing code keeps working.

### Changed
* A request that runs out of time no longer takes the connection down with it: only that request is finished, while the connection, its prepared statements and its other requests in flight carry on. The node is not counted as failed either, so one expensive query cannot push a healthy node out of rotation. Requests that run out together are finished together and reported as one failure.
* An async statement's budget runs from when its request was sent, not from when you get around to waiting for it, so it gets the same total allowance either way.
* Deadlines now bound the read itself instead of only deciding whether to start one. A request timeout, a wait bound or the heartbeat used to be noticed only when the read the client was sitting in came back, so the transport's receive timeout was the granularity of every deadline — with the old defaults a 30s request timeout fired somewhere between 30s and 45s. Each read is now given the earlier of the caller's deadline and the moment the heartbeat is next due, so deadlines fire when they are due and the two layers are genuinely independent.
* Disabling the transport receive timeout is no longer dangerous. `SO_RCVTIMEO => ['sec' => 0, 'usec' => 0]` and `StreamNodeConfig(timeoutInSeconds: 0)` mean "no stall window", not "no deadlines": request timeouts, wait bounds and the heartbeat all still fire on schedule. Equally, raising it no longer blunts them, so it can be set purely for what it is — how long a connection may make no progress at all before that counts as a transport failure.
* The transport stall window is now the fallback for a read that nothing else bounds. A read timeout is ignored while the caller's deadline or the next heartbeat will still end the wait — a slow coordinator looks exactly like a quiet one — but with no wait bound, no request budget and no heartbeat, the stall window is the only judgement available and it is the transport's own, so it fails the connection instead of being waited out forever. This is what `SO_RCVTIMEO`/`timeoutInSeconds` is left governing once deadlines are handed to the read itself.
* Requests keep their deadlines during any wait, but only a wait that was asked about a request reports it. Waiting for the next event or response finishes an expired request quietly and runs its course; you find out from the statement, which raises `RequestTimeoutException` when you next touch it. This keeps an event loop from being interrupted by an unrelated query.
* Statements still in flight when the connection closes are marked abandoned and fail immediately, instead of silently reconnecting and then blocking for a full timeout on a connection that could never answer them.
* A request has no stream id until it is sent, so stream id 0 is now an ordinary id like any other rather than standing for "unassigned".
* Across the API, `requestTimeoutInSeconds` always means "how long the server may take to answer" and `timeoutInSeconds` always means "how long this call may block". Reaching a wait bound simply ends the wait and leaves the statements untouched and still waitable.
* The non-blocking calls now keep the connection's bookkeeping too. `tryResolveStatement()`, `tryResolveStatements()`, `tryReadNextResponse()`, `tryReadNextEvent()` and `drainAvailableResponses()` still never wait, but they now enforce request budgets and send the heartbeat like the waits do — so a statement that is only ever polled runs out of time (and releases its stream id) instead of staying pending for good, and a connection that died quietly is noticed by an application that only polls. In particular `Cassandra\Statement::tryGetResult()` and friends can now raise `RequestTimeoutException`.
* Waiting for events no longer fails on a quiet cluster. `waitForNextEvent()` used to throw as soon as no event arrived within the receive timeout — dropping the connection and marking the node as failed — which made a quiet cluster indistinguishable from a broken one and left polling `tryReadNextEvent()` as the only workable pattern. It now simply waits, and the new heartbeat notices a connection that really did die.
* Default I/O timeouts were raised and aligned across both transports: receive 15s (was 10s socket, 30s stream), socket send 10s (was 5s). The old socket default sat exactly on Cassandra's own 10s `range_request_timeout`, making a server-side timeout a race with the client's. `TRUNCATE` (60s server-side) still needs an explicit increase.
* The library now requires no PHP extension at all. `ext-ctype`, `ext-mbstring` and `ext-filter` were all previously used; all three uses have been removed rather than declared in `composer.json`, so the library keeps working on minimal PHP builds.
* `Cassandra\TypeNameParser` no longer uses `ext-mbstring`.
* `Cassandra\Connection\Socket` no longer uses `ext-filter`.
* `Cassandra\Value\Varint`, `Cassandra\TypeNameParser` and the decimal calculators no longer use `ext-ctype`.
* Waiting no longer costs a walk over every request in flight. Each pass of every wait asks for the earliest deadline among the statements outstanding, which meant walking all of them — quadratic in the number of responses drained on a connection with many async requests in flight. The answer is now remembered until something it is computed from changes, and `waitForAllPendingStatements()` no longer builds a filtered copy of the pending map once per pass.
* `Cassandra\Connection::getNode()` is deprecated. It hands out the live transport, which is the session's: writing to it or closing it desynchronises the response reader and strands every request in flight. Use `isConnected()` for whether there is a connection.
* `Cassandra\Connection` was split up. It is now the public API and nothing else: it builds requests out of what a caller passes and hands everything that touches the node to a `Cassandra\Connection\Session`, which is composed of one class per concern — `RequestExecutor` (getting a request onto the wire), `ResponseDispatcher` (what becomes of an answer, including auto-preparation and repreparation), `StatementRegistry` (the requests in flight and their budgets), `StreamIdPool` (the stream id space), `HeartbeatMonitor` (when a silent connection is probed), `NodeConnector` (which node to open a connection to), `Handshake` (protocol version and startup option negotiation), `PreparedResultCache`, `Deadline` and `ListenerRegistry`. Everything below `Connection` is marked `@internal`. **No public API changed** — same classes, same methods, same signatures, same behaviour; only code that reached into `Connection`'s private state by reflection is affected.

* Empty values are now modelled the way Cassandra models them, which changes what `fromBinary()` returns. Cassandra's `AbstractType` answers two separate questions about a zero-length value — `allowsEmpty()`, whether a node accepts one at all, and `isEmptyValueMeaningless()`, whether it denotes null — and the driver now declares both per type, on `Cassandra\Value\ValueBase`. `Cassandra\Value\ValueBase::fromBinary()` and `Cassandra\ValueFactory::getValueObjectFromBinary()` are therefore nullable: an empty value of a type whose serializer deserializes one to null (`bigint`, `boolean`, `counter`, `decimal`, `double`, `float`, `inet`, `int`, `timestamp`, `timeuuid`, `uuid`, `varint`) now returns `null` instead of a fabricated zero/false or an exception. The types where an empty value is a value of its own return it as before — `ascii`, `text`, `varchar`, `blob` and `custom` give the empty string, and `tuple`/`udt` give components that are all null — and those classes narrow their return type back to `static`, so a caller of e.g. `Cassandra\Value\Varchar::fromBinary()` still has a non-null guarantee. A type that admits no empty value at all (`smallint`, `tinyint`, `date`, `time`, `duration`, `list`, `set`, `map`, `vector` — each of whose serializers demands an exact width) refuses one. Reading rows is unaffected: an empty cell is resolved from its length before any decoder is reached, and `Cassandra\ValueFactory::allowsEmptyValue()` / `isEmptyValueMeaningless()` expose the same two predicates by `Cassandra\Type`.
* `Cassandra\Request\Options\QueryOptions` / `ExecuteOptions` / `BatchOptions` now reject a `pageSize` or `nowInSeconds` that does not fit in a signed 32-bit integer, with a `Cassandra\Exception\RequestException` (`REQUEST_INVALID_PAGE_SIZE`, `REQUEST_INVALID_NOW_IN_SECONDS`). Both go out as an `[int]`, and `pack('N', …)` takes the low four bytes of whatever it is given without complaint, so a larger value did not fail — it reached the coordinator as a different number: a page size of 2^31 arrived as -2^31, and one of 2^32 + 100 as 100, silently running the query with a page size nobody asked for. The same bound `Cassandra\Request\Request::encodeQueryValuesAsBinary()` already held bound integer values to.

### Fixed
* `Cassandra\Value\MapCollection` and `SetCollection` now serialize entries in the comparator order of their declared CQL type instead of PHP insertion order. This keeps frozen collection values canonical on every supported Cassandra version. Comparator-equal duplicate map keys and set elements are refused with `VALUE_MAP_DUPLICATE_KEY` / `VALUE_SET_DUPLICATE_ELEMENT` instead of producing an invalid collection.
* Named bind markers now preserve quoted identifier case. Direct `QUERY` requests retain the exact spelling of quoted markers, prepared statements require exact matches for mixed-case server marker names, and distinct quoted markers such as `"Foo"` and `"foo"` can be bound together. Lowercase unquoted markers retain the case-insensitive convenience matching they had before.
* Connecting now tries the next configured node when TCP succeeds but OPTIONS, STARTUP, authentication or the initial keyspace switch fails. A node is recorded healthy only after the whole Cassandra handshake succeeds, and the last specific project exception is preserved if every candidate fails.
* `QUERY` and `EXECUTE` now reject default timestamps forbidden by the negotiated protocol (`REQUEST_INVALID_DEFAULT_TIMESTAMP`): every negative value on v4/v5 and the minimum signed 64-bit value on v3. Other negative v3 timestamps remain supported for protocol compatibility.
* Authentication accepts the non-empty string `"0"` as a username or password instead of treating it as missing through PHP truthiness.
* `Cassandra\TypeNameParser` now rejects fractional and scientific-notation vector dimensions (`TYPENAMEPARSER_VECTOR_DIMENSIONS_NOT_INTEGER`) instead of truncating or converting them to integers.
* `Cassandra\Value\ListCollection`, `SetCollection`, `MapCollection` and `Vector`: a null element reported `Cannot get type object for value` — a `ValueFactoryException` about the type system, for what is a plain fact about the data. Each now raises a `Cassandra\Exception\ValueException` naming the position and saying that CQL has no null inside a collection (`VALUE_LIST_NULL_ELEMENT`, `VALUE_SET_NULL_ELEMENT`, `VALUE_MAP_NULL_VALUE`, `VALUE_VECTOR_NULL_ELEMENT`). Tuples and UDTs are unaffected: a null field is legitimate there and is still encoded as a -1 length.
* `Cassandra\Value\Decimal`: a value given in scientific notation kept the leading zeros the mantissa had once the point was shifted, so `Decimal::fromValue('0.5e1')->getValue()` was `"05"` and `'0e5'` was `"000000"` — neither a canonical decimal, and neither what the same number spelled plainly produced. The wire encoding cannot show a leading zero, so the value read back from a node did not match the one written. A sign on a value whose digits are all zero went the same way: `'-0'` and `'-0.0'` came back from a node as `"0"` and `"0.0"`, the unscaled varint of such a decimal being zero, which has no sign. Both spellings are now folded at construction. A negative value that merely looks like zero at its integer digit is untouched — `'-0.100'` has an unscaled value of -100 and keeps its sign and its scale.
* `Cassandra\Value\Varint::fromBinary('')` decoded an empty value as `0` rather than reporting null. `unpack('C*', '')` hands back an empty array rather than `false`, so the accumulator loop simply never ran and nothing noticed; zero has an encoding of its own (`"\0"`), so the two were indistinguishable. Rows were never affected — an empty varint cell is resolved from its length — but `Cassandra\Value\Decimal::fromBinary()` reached it for any decimal whose body was exactly four bytes, which is a truncated decimal rather than one with an unscaled value of zero, and is now refused.
* `Cassandra\Response\StreamReader`: an empty `tuple` or `udt` cell decoded to `null` instead of to a value whose components are all null. Cassandra's `TupleType` admits an empty value and leaves `isEmptyValueMeaningless()` at false, so one denotes a tuple whose components are all absent; `UserType` extends it and inherits the same reading. A null cell (length -1) is still null, and the two are now distinct.
* `Cassandra\Value\MapCollection`: a `map<text, …>` — or `ascii`, `varchar`, `blob` or `custom` — whose key spelled a whole number could not be encoded at all, so `['123' => …]` failed with `Invalid varchar value; expected string`. The same fold that cost `map<boolean, …>` its encoding is at work here: PHP turns an array key that is the canonical decimal spelling of an integer into an int, so `'123'` is `123` the moment the literal is written — and again when `fromStream()` puts the key it decoded into the array, which cost such a map its round trip as well. The caller had no way round it either, the coercion happening at the array literal rather than anywhere the driver could see. The int is now spelled back out for the key types whose values are strings, as `Cassandra\Request\Request::encodeQueryValuesAsBinary()` already did for bind marker names. `uuid`/`timeuuid` are covered too, for the raw 16-byte form `UuidEncodeOption::AS_BINARY` decodes to.
* `Cassandra\Value\Decimal`: a value with more than 100 000 fraction digits was encoded happily and then refused on the way back in, so it could be written to a node and never read from one. `fromBinary()` bounds the scale — decoding expands the value into a string whose length grows with it, so an unbounded scale is a decode-side denial of service — but nothing applied the same bound on the way out, and a plain decimal string keeps its fraction verbatim. The bound is now checked at construction as well, so the two sides agree exactly: the largest decimal this class accepts is one it can also read back. The encode-side guard that existed covered only scientific notation (`MAX_EXPONENT_MAGNITUDE`), not a long literal fraction.
* `Cassandra\Response\Result\RowsResult::fetch()`: with `FetchType::BOTH`, a quoted numeric column name shifted every positional key after it by one, so `$row[1]` held the first column's value rather than the second's. The two views share one key space — PHP folds a column named `"0"` into the very int a position uses — and the positional value was appended, so such a name took the key the next append would have had. The positional index is now written explicitly and restored after the names, so every column is reachable at its own position. Where a name collides with a position another column already holds, the positional view wins, that being the one a caller reads by number. The documented key order (`['id' => …, 0 => …, 'name' => …, 1 => …]`) is unchanged.
* `Cassandra\Connection\PreparedResultCache`: an entry held the caller's `Prepare` object rather than a copy of it, so it followed that request's later sends. A request is addressed on its way to the wire and keeps what it was given, so `applyDefaultKeyspace()` replaces the keyspace of one that is sent again — and an application that reused a single `Prepare` across a `setKeyspace()` on v5 left the entry naming a keyspace other than the one it is filed under. The repreparation path rebuilds its `PREPARE` out of exactly that request, so an `UNPREPARED` for the statement id would have prepared and executed the query against the wrong keyspace, with nothing to show for it. The cache now stores a copy.
* `Cassandra\Connection`: a wait for a request's answer no longer resumes on a connection that was replaced under it. A wait matches its answer on the stream id, which is only meaningful on the connection that handed the id out — so where the connection had been replaced mid-wait, the wait reconnected on its next pass and the fresh id space was free to hand the same number to another request, whose answer was then returned as this caller's result. Every failure inside the driver that replaces a connection raises on its own, and an async statement is caught by `isAbandoned()`, which left one way in: an event or warnings listener — which runs from inside the read, in the middle of the wait — calling `disconnect()` itself. In practice that also cost the caller its whole request budget before reporting a timeout for a request the node had answered. Such a wait now raises a `Cassandra\Exception\ConnectionException` (`CONNECTION_WAIT_CONNECTION_REPLACED`) at once; send the request again.
* `Cassandra\Connection`: a repreparation or auto-prepare could fail to encode a request that had worked before. The driver builds requests out of other requests' options — the `PREPARE` an auto-prepared query needs, the `PREPARE` and `EXECUTE` a repreparation sends — and options carry the keyspace but not the record of who put it there, so a keyspace the *driver* applied was inherited as one the *caller* had named. A keyspace the caller named is never taken back, so such a request bound for a v3/v4 connection kept an option those versions cannot express and was refused with a `RequestException` instead of being addressed the way v4 addresses one. Reachable by preparing on a v5 connection and executing on a v4 one — a second `Cassandra\Connection`, or the same one after it renegotiated down on reconnect — and then being answered with `UNPREPARED`. `Cassandra\Request\Request::adoptDefaultKeyspaceMarkerFrom()` is the new hook; only relevant to code that implements its own request type.
* `Cassandra\Connection`: the heartbeat dropped a healthy connection whenever a single answer took longer to arrive than `heartbeatTimeoutInSeconds`. The probe was judged on its own clock alone, and nothing that arrived afterwards could retire it — so a connection delivering a wide page, a blob column, or anything at all over a slow link was declared dead mid-transfer, with the node put into its cooldown for it. Frames are serialised on one socket, so the probe's own `SUPPORTED` cannot overtake the response it is queued behind; and while a large frame is being assembled none completes, so nothing but the bytes themselves distinguishes that transfer from silence. The trigger was the ordinary case of an idle connection woken by a big query: the wait that sends the request finds the probe due and sends it, and the answer then takes longer than the timeout to stream in. The heartbeat timeout now runs from the last sign of life rather than from when the probe went out, where a sign of life is any byte read off the connection — `Cassandra\Connection\Node::getReceivedByteCount()` is the new signal. A connection that is genuinely dead produces no bytes at all, so it is still caught after roughly interval + timeout, exactly as before.
* `Cassandra\Connection`: an unanswered heartbeat no longer records the node as failed. The connection is dropped, but a probe that went unanswered on one socket says that socket is finished, not that the node is bad — and a node in its cooldown is tried last, which on a single-node configuration makes the reconnect wait for a node it has no alternative to. This matches `maxOrphanedStreams`, which has always left the node's record alone for the same reason.
* `Cassandra\Connection`: a client with every stream id in flight could lose its connection to its own backlog. With the id space exhausted the heartbeat reported no read bound at all, since it could not claim an id to send a probe with — and a read that nothing bounds is exactly the state in which the transport's stall window is treated as the last judgement available and fails the connection. It took all three at once: every id outstanding, all of those requests unbounded, and a caller waiting without a deadline of its own. The heartbeat now reports a bound one interval out instead of none, which costs one wake per interval, cannot spin, and leaves the stall window meaning nothing while the client is merely busy.
* `Cassandra\Connection`: the connection's keyspace was dropped from the first request whenever the connection was opened by that request rather than by an explicit `connect()`. Whether the keyspace travels with a request depends on the negotiated protocol version — from v5 it is a request option, before that a `USE` at handshake time settles it — and the decision was made while the request was being built, from `getProtocolVersion()`, which before the handshake answers with the *initial* version rather than the negotiated one. Guessed low (the v4 default) against a v5 node, the keyspace was left off the request and no `USE` was sent either, so it reached the coordinator with no keyspace at all; guessed high (`initialProtocolVersion: V5`) against a v4 node, an option was attached that encoding the request then refused with a `RequestException`. The keyspace is now filled in by `Cassandra\Connection\RequestExecutor` on the way to the wire, where the negotiated version is known, so building a request needs no connection and asks no question it cannot answer.
* `Cassandra\Connection\PreparedResultCache`: the cache is keyed on `(query, keyspace)`, but a request built by hand carried no keyspace, so on v5 the same CQL prepared from two connections on different keyspaces shared a cache slot. The keyspace is now filled in before the key is taken.
* `Cassandra\Connection::setKeyspace('')` no longer sends `USE ;` on protocol v3/v4. An empty keyspace is the absence of one, not a keyspace to switch to. See the breaking change above for what it does on a connected v3/v4 connection instead.
* `Cassandra\Connection\PreparedResultCache`: switching keyspace on protocol v3/v4 handed out the previous keyspace's prepared statements. A `PREPARE` cannot carry a keyspace before v5, so the cache key is the query alone there, and nothing emptied the cache when `setKeyspace()` moved the node's session elsewhere — the next `prepare()` of the same CQL was answered out of the cache with an id prepared in the keyspace just left, and every `execute()` on it silently ran against that keyspace's table, with no error to show for it. The cache is now emptied when a v3/v4 keyspace switch succeeds. From v5 it is kept, the keyspace being part of the key there.
* `Cassandra\Connection`: a node that answers the `AUTH_RESPONSE` with an `AUTH_CHALLENGE` is now reported as the unsupported authenticator it is (`CONNECTION_AUTH_CHALLENGE_UNSUPPORTED`, naming the authenticator class), instead of as `Authentication failed.` Only single-round password authentication is implemented, and reporting a multi-round SASL exchange as a rejected password sent people looking for a typo in credentials the node never passed judgement on.
* `Cassandra\Connection`: a statement given up on because its connection went away while a wait was reading is no longer re-marked as timed out by that wait. It stayed abandoned in every case but this one, so the same failure was reported as a `RequestTimeoutException` or a `StatementException` depending on which side of a read the connection was lost on.
* `Cassandra\Connection::setKeyspace()` no longer records a keyspace whose `USE` the node refused. On protocol v3/v4 the keyspace is the node session's, and a refused `USE` left it on the old one — but the new name was kept regardless, so the call threw and then every following request ran against the previous keyspace while `getKeyspace()` named the other. It also armed the next `connect()` with a `USE` that fails the handshake, turning one rejected call into a connection that could no longer be opened. The previous keyspace is restored when the switch fails.
* `Cassandra\Connection`: a request object sent more than once kept the keyspace of its first send. The connection's default is written onto the request on its way to the wire, and a request that already carried one was left alone — which is right for a keyspace the caller named, but a request re-sent after `setKeyspace()` carried the connection's *own* earlier default and was left alone just the same, so it went on running against the keyspace the connection had left, silently and without error. The two are now told apart.
* `Cassandra\Connection`: a request object re-sent on protocol v5 after `setKeyspace('')` still carried the keyspace of its earlier send. Moving a v5 connection off its keyspace is a change like any other — the keyspace travels per request there, so an empty one means the absence of one — but with no keyspace to apply there was nothing to overwrite the old default with, and the statement went on reaching the keyspace the connection had left while `getKeyspace()` named none. A default the driver put on a request is now taken back whenever the connection has none to give, as it already was for a send that renegotiated below v5.
* `Cassandra\Connection\ResponseReader`: a response frame header is now refused if it announces a body larger than the 256 MB the protocol allows, or one that does not fit a signed int on 32-bit builds, instead of being taken at face value. The length is an unsigned 32-bit field, so a corrupted or hostile header could ask for up to 4 GiB, which the transport would assemble one socket read at a time — spending the memory before anything went wrong enough to notice. It is now rejected at the header, before a byte of the body is read.
* `Cassandra\Connection\Socket`: an interrupted `socket_select()` is no longer at risk of being read as a broken one. PHP keeps the last socket errno until it is cleared, and the errno is the only thing that tells `EINTR` from a genuine failure — so an `EWOULDBLOCK` left behind by an earlier read could turn a signal into a `SOCKET_SELECT_FAILED` that cost the connection. The error is now cleared before every `socket_select()`, and before the `socket_create()` in the connect loop, where a previous candidate address's failure was otherwise reported as this one's.
* `Cassandra\Connection\Socket`: on the blocking-I/O fallback, a read interrupted by a signal re-entered `socket_read()` under the `SO_RCVTIMEO` it was already running with. That option arms a duration rather than a deadline, so each signal handed the read the caller's whole remaining budget again, and a stream of them could overshoot a request timeout by a multiple of it. The timeout is now re-narrowed against the read deadline on every retry.
* `Cassandra\Connection`: a partially read response was carried across connections and desynchronised the next one. A bounded read can come back having consumed a frame's header but not its body — the two share one absolute deadline, so this is ordinary rather than exceptional — and the reader keeps the header so that the next read resumes the same frame. That state survived `disconnect()`, so the bytes still owed were taken from whatever connection came next: the first response on the fresh connection was consumed as the body of a frame nobody was going to send, and every response after it was parsed at the wrong offset. Reachable from every path that replaces a connection — the orphaned-stream limit, a heartbeat timeout, a failed handshake, an explicit `disconnect()`. The half-read frame is now dropped with the connection it belongs to.
* `Cassandra\Connection\Socket` / `Cassandra\Connection\Stream`: on the blocking-I/O fallback, whether a read had been cut short by the caller's deadline or by the transport's stall window was decided by measuring the elapsed time and comparing it against the stall window. Where nothing narrowed the read the two are the same duration, so the comparison came down to scheduling jitter, and landing on the wrong side turned a connection that had genuinely stalled into another silent retry. Which of the two bounds was armed is now recorded when it is applied.
* `Cassandra\Connection`: the heartbeat is no longer sent from a non-blocking call when every stream id is in use. Claiming an id in that state waits for one to be released, which reads — so `tryResolveStatement()`, `tryReadNextResponse()`, `tryReadNextEvent()` and `drainAvailableResponses()` could block for a full request timeout. The probe is skipped instead; requests going unanswered still take the connection down through `maxOrphanedStreams`.
* `Cassandra\Connection\Socket`: reconnecting reused the receive timeout tracked for the previous socket, so the first read that needed a narrower one skipped applying it and ran under the wider stall window instead of the caller's deadline. Only reachable on the blocking-I/O fallback. `Cassandra\Connection\Stream` already reset this on connect.
* `Cassandra\Connection::waitForAnyStatement()`: a statement answered in the very pass that the wait bound expired was reported as nothing having arrived. The set was only checked for readiness at the top of each pass, so a read that resolved a statement and a deadline that ended the wait in the same pass returned `null` — leaving the caller to conclude that none of their requests had come back while the answer sat on the statement. The set is looked at once more before giving up.
* `Cassandra\Connection::waitForAnyStatement()`: waiting on an empty array never returned. Nothing could become ready, and with the default `$timeoutInSeconds` of `null` there was no bound to end the wait either, so it read for good — sending a heartbeat every interval — on a connection that was perfectly healthy. It now returns `null` at once.
* `Cassandra\Connection::waitForStatements()`: a statement that can never be resolved here — one sent on another connection, or already given up on — was only reported once every statement before it in the array had been answered, and not at all when the wait bound fired first, because each pass stopped at the first unresolved statement. Every statement is now checked per pass, as `waitForAnyStatement()` already did.
* `Cassandra\Connection`: a node whose answer could not be handled — the repreparation limit reached, or an event or warnings listener of the application's raising — was not credited with having answered, so a node that replied promptly counted as silent towards the heartbeat and its health record. Both are now recorded as soon as a complete frame has been read, before anything is made of it.
* `Cassandra\Connection\HeartbeatMonitor`: an answered probe that had not yet been retired kept reporting its timeout as the instant reads should come up for air. That instant is in the past, so every read returned at once until the probe was cleared. Only reachable through the polling calls, which can return without reading and so without clearing it.

* `Cassandra\Connection\Socket` / `Cassandra\Connection\Stream`: on the blocking-I/O fallback — taken when the transport cannot be switched to non-blocking mode — a read with a deadline already past returned empty-handed without looking at the socket at all, since reading would have sat in the stall window. That is the read every non-blocking call makes, so `tryResolveStatement()`, `tryReadNextResponse()`, `tryReadNextEvent()` and `drainAvailableResponses()` could never take anything off such a connection and reported it idle whatever the server sent. Readiness is now settled with a zero-timeout `select()` first, which works on a blocking socket just as well, and the data is served without waiting.
* `Cassandra\Connection`: a follow-up request (a repreparation, an auto-prepared execute) whose connection had been closed under it opened a replacement connection and re-sent on it. The stream id it carries belongs to the connection that is gone, whose id space a new connection starts over, so the statement was registered at an id the new connection was free to hand to another request — which then failed with "stream ID already in use" — and the statement had been abandoned along with its connection anyway, so it could never be resolved. It is now given up on with a `Cassandra\Exception\ConnectionException`.
* `Cassandra\Value\Date`: the number of days since the epoch was computed by diffing the supplied value against a `1970-01-01` base built in the ambient (default) timezone. For a `DateTimeInterface` carrying a time-of-day in a different timezone this could yield a date off by one day. Both ends are now anchored at UTC midnight and a `DateTimeInterface` is reduced to its own calendar date (`Y-m-d`), so the stored day count is exact and independent of `date_default_timezone_*`.
* `Cassandra\Value\ListCollection` / `Cassandra\Value\SetCollection`: `getBinary()` encoded every element through `ValueFactory::getBinaryByTypeInfo()`, which rejects a `Cassandra\Value\ValueBase` instance, so a list or set whose elements were already `Value` objects (for example a `list<duration>` or a `set<uuid>` built from `Value` objects, or a nested `list<tuple<…>>`) threw a `Cassandra\Exception\ValueException` during encoding — even though the same object works as a map value, UDT field or tuple element. List and set elements now honour a pre-built `ValueBase` via `getBinary()`, matching `Cassandra\Value\MapCollection`, `UDT` and `Tuple`.
* `Cassandra\Connection\FrameCodec`: a request larger than the maximum frame payload size (128 KiB) triggered an infinite loop, because the chunking offset and remaining-length counters were reset on every iteration. Large requests are now split into frames correctly.
* `Cassandra\Connection\Socket` / `Cassandra\Connection\Stream`: the partial-write loop used `while ($data)`, which treats a remaining single byte `"0"` (`0x30`) as falsy and stops early, silently dropping that byte and sending a truncated frame to the server. The loop now terminates on `$data !== ''`.
* `Cassandra\Connection\FrameCodec`: a request whose serialized size was exactly the maximum frame payload size (131071 bytes) was sent through the multi-frame path as a single non-self-contained frame instead of one self-contained frame. The boundary is now handled by the single-frame path.
* `Cassandra\Connection\FrameCodec`: the frame reader returned early on a zero-length payload without consuming the 4-byte payload CRC32 trailer, while `writeFrame()` always emits one. A zero-payload frame from the server would leave 4 stray bytes in the stream and fail the next header CRC24. A zero-length payload is no longer treated as a special case; its CRC32 trailer is read and verified like any other frame's.
* `Cassandra\Request\Query` / `Cassandra\Request\Execute`: the `serialConsistency` request option was encoded as the enum instance instead of its protocol code, so any query using it was rejected by the server with "Invalid consistency for conditional update". Lightweight transactions with an explicit `SerialConsistency` now work.
* `Cassandra\Connection`: cached prepared statements could not be reprepared after the server invalidated them (for example following a schema change). A cache hit returned a result with no associated request, and the repreparation then consulted the same stale cache entry and looped forever. Prepared statements now reprepare transparently after invalidation.
* `Cassandra\Connection::queryAsync()`: an asynchronous query that relied on auto-preparation (any native, untyped bind value) failed on protocol v5 with `Server protocol version does not support request option "keyspace"`, because the internally built prepare request was left at the default protocol version and stream id.
* `Cassandra\Connection::waitForAnyStatement()`: hung when every supplied statement had already been resolved, because it blocked on a response before checking readiness.
* `Cassandra\Connection::disconnect()`: unresolved asynchronous statements from the previous connection were left registered, so `waitForAllPendingStatements()` blocked forever after a reconnect. The per-connection stream state is now reset on disconnect.
* `Cassandra\Response\StreamReader::readValue()`: zero-length ("empty") values for fixed-length types desynced the row decoder. Cassandra distinguishes null (`[bytes]` length `-1`) from empty (length `0`), and an empty value is legal for every fixed-length type. Both the fast path (`INT`, `DOUBLE`, `BOOLEAN`, `UUID`, `BIGINT`, …) and the `Cassandra\Value\ValueWithFixedLength` path (`TIMESTAMP`, `DATE`, `TIME`, `SMALLINT`, `TINYINT`, `FLOAT`, …) ignored the declared length and always read a fixed number of bytes, consuming bytes belonging to the next column and misaligning the rest of the row and every remaining row in the page. `readValue()` is now authoritative about the cell frame: it maps a zero length to `null` (consistent with `-1`/`-2`) and forces the stream offset to the end of the declared value after decoding, and `Cassandra\Value\ValueWithFixedLength::fromStream()` honours the passed length.
* `Cassandra\Connection::connect()`: a handshake that failed without a transport error — a request timeout on the OPTIONS or STARTUP, a rejected authentication, an unusable protocol version — left the socket open. `isConnected()` went on reporting `true`, every later request was written to a connection the node had never accepted a STARTUP on, and the heartbeat stayed disabled for good because it is gated on a completed handshake. The connection is now closed before the failure is raised.
* `Cassandra\Connection::queryAsync()`: an asynchronous query that relied on auto-preparation never consulted the prepared-statement cache, so it paid for a PREPARE on every call even though the result was already cached (and was written back to the cache each time). The cache is now looked up for the request that is actually about to be sent, matching the synchronous path.
* `Cassandra\Connection\Stream`: a signal arriving during `stream_select()` — from `pcntl` alarms, `SIGCHLD`, anything — was reported the same way as a real select failure and tore the connection down, marking the node as failed. Interrupted selects are now retried for as long as the transport's stall window allows, as the socket transport already did for `EINTR`.
* `Cassandra\Connection`: waiting on a statement that this connection does not know — one from another `Connection`, or left over from before this one was replaced — waited for an answer that could never arrive, for as long as the caller was willing to and forever when the wait was unbounded. It contributes no deadline of its own either, since a wait bounds itself by the requests this connection has in flight. It is now rejected at once with a `Cassandra\Exception\StatementException`.
* `Cassandra\Connection`: a statement whose answer arrived but could not be handled was left neither pending nor finished, and its stream id was lost for the lifetime of the connection. Handling an answer can prepare and re-send the statement, cache a prepared result or run the application's warnings listeners, and any of that can fail — most plainly when a node keeps answering `UNPREPARED` and the driver stops repreparing. The statement had already been taken out of the pending map by then, so its owner waited on it for good and was told, misleadingly, that it belonged to another connection. Such a statement is now given up on (`Cassandra\Statement::isAbandoned()`) and its stream id released.
* `Cassandra\Connection::asyncRequest()` and the async helpers built on it: a stream id claimed for a request that then failed before reaching the node — an unencodable auto-prepared query, say — was burned for the lifetime of the connection. Auto-preparation is now resolved before an id is claimed, as the synchronous path already did, and an id is put back whenever nothing was written on it.
* `Cassandra\Connection\Socket`: on the blocking-I/O fallback, a read deadline less than a microsecond away rounded to `SO_RCVTIMEO => {sec: 0, usec: 0}`, which the socket option reads as *no* timeout — so a read meant to return almost immediately blocked until the peer said something. The read is now skipped instead, as it is for a deadline that has already passed. `Cassandra\Connection\Stream` skips it too, for the same reason.
* `Cassandra\Connection`: the repreparation count of the synchronous path was kept on the connection rather than on the call, so a request started from inside one — an event or warnings listener issuing a query of its own while a repreparation was being handled — inherited that depth and gave up after fewer repreparations than it was entitled to. Each chain now carries its own count.
* `Cassandra\Connection\Socket` / `Cassandra\Connection\Stream`: on a transport that could not be switched to non-blocking mode, a read asked not to wait at all still fell through to a blocking `socket_read()`/`fread()` bounded only by the receive timeout — so `tryReadNextResponse()`, `tryReadNextEvent()`, `tryResolveStatement()`, `tryResolveStatements()` and `drainAvailableResponses()`, all of which promise never to wait, could block for up to 15s. Such a read now returns empty-handed; anything already buffered is served as before.
* `Cassandra\Connection`: the heartbeat could be judged against a read that never happened. `tryResolveStatements()` returns before reading when every statement it was given is already resolved, as does `drainAvailableResponses(0)`, and both still ran the probe check — so a poll loop could declare a healthy connection dead over an answer that was sitting unread in the receive buffer. The probe now only runs when the call got as far as reading; request budgets are kept either way.
* `Cassandra\Connection::waitForStatements()` / `waitForAnyStatement()`: a request that was not among the statements handed in could overshoot its deadline for as long as the wait ran. Both bounded their reads by the budgets of the waited set alone, while every other wait bounds them by every request in flight, so a statement with a short budget waited on nowhere kept its stream id until the wait happened to end for some other reason — with a 30s statement in the set, a 0.5s one beside it was given up on 30s late. Both now bound the read by all in-flight budgets; which of them is the caller's failure to report is unchanged.
* `Cassandra\Connection::disconnect()`: the negotiated protocol version survived the connection it was negotiated on. Every other piece of per-connection state is reset there, but a reconnect — possibly to a different node, since the selector reorders and a failed node is skipped — opened its handshake at the old version instead of `ConnectionOptions::$initialProtocolVersion`. A node that could not answer at that version was then read as a protocol mismatch and failed outright, which is precisely what the conservative initial version exists to prevent. This also restores what `getProtocolVersion()` documents: before connecting it reports the initial version.
* `Cassandra\Connection`: waiting for a stream id watched only the recycling pool, which a reconnect empties. If the connection was replaced while the wait ran, all 32768 ids were free but none of them were in that pool, so the wait sat out its whole budget and then reported the id space as exhausted. The counter is now re-checked on every pass.
* `Cassandra\Connection`: a chained follow-up request (a repreparation, an auto-prepared execute) left its statement unmarked when it failed before the write — no node to reach, or a stream id unexpectedly in use. The statement was then neither pending nor finished, and reported as belonging to another connection rather than as abandoned. Every failure path now marks it.
* `Cassandra\Connection::syncRequest()`: a failure that was neither a node failure nor a timeout — a frame the reader could not make sense of, above all — leaked its stream id, which was then lost for the life of the connection. It is now parked like a given-up-on request's and released if its answer turns up.
* `Cassandra\Connection\Socket` / `Cassandra\Connection\Stream`: a transport failure was reported twice — once as the driver's own `NodeException`, and once as a PHP warning from the underlying call. Both transports read the error and raise an exception carrying far more context, so the warning was a duplicate; but it also reached the application first, so anything that turns warnings into exceptions (Symfony's and Laravel's error handlers, `set_error_handler` throwing `ErrorException`) got a bare `ErrorException` in place of the driver's report — and got it from `Connection::disconnect()` while the real failure was still propagating, and from the transports' destructors. This affected ordinary conditions, not edge cases: a connection reset by the peer, a refused connection, a signal interrupting `select()`, and closing a connection whose peer had already gone. The calls whose errors the transports inspect themselves no longer raise diagnostics of their own; nothing is lost, since every one of them is reported through the exception instead. Connecting to a host that resolves to both IPv6 and IPv4 no longer warns on the way to a connection that succeeds.
* Fixed several misspelled exception context keys (`proocol_versions_*` → `protocol_versions_*`, `required_protocol_verison` → `required_protocol_version`).
* `Cassandra\Connection\ResponseReader`: the frame header's stream id was decoded as an unsigned `[short]`, but the protocol defines it as signed and server-initiated responses (events) use `-1`. As a result `Cassandra\Response\Response::getStream()` reported `65535` for every event, giving misleading values in error contexts and exception payloads. The stream id is now sign-extended to its correct negative value.
* `Cassandra\VIntCodec::decodeUnsignedVint64()`: the decoder read the continuation bytes indicated by the leading byte without checking that the input actually contained them. On truncated input PHP emitted an "undefined array key" warning and treated the missing byte as `0`, silently returning a wrong integer. The decoder now validates the length up front and throws a `Cassandra\Exception\VIntCodecException`, mirroring the stream-based `readUnsignedVint64()`.
* `Cassandra\Connection\Socket::write()`: after a partial write the inner loop re-invoked `socket_write()` without re-entering `selectSocketForWrite()`, so against a slow peer it busy-spun on `EAGAIN`/zero-byte writes (burning CPU) until `sendTimeout` elapsed. The loop now returns to the outer loop and waits for the socket to become writable again before retrying.
* `Cassandra\Connection\Socket::connect()`: the socket was always created with `AF_INET`, so connecting to an IPv6 host failed. The host is now resolved up front with `socket_addrinfo_lookup()` (`getaddrinfo()`), which reports the address family of every result, so IPv4 literals, IPv6 literals and hostnames are all handled uniformly. This also fixes hostnames that only publish `AAAA` records: an earlier attempt at this chose the family by testing the host for an IPv6 literal, which left every name on `AF_INET`, where `socket_connect()` resolves via `gethostbyname()` and can never see an IPv6 address. IPv6 literals are additionally accepted in bracketed form (`[::1]`), and a host that resolves to nothing now fails with a dedicated `SOCKET_HOST_RESOLUTION_FAILED` error rather than an opaque connect failure.
* `Cassandra\Connection\Socket::connect()`: when a hostname resolved to several addresses, only the first was ever tried, so a dual-stack host whose first address was unreachable failed to connect even with a working second address. Every resolved address is now tried in turn, and the last error is reported if all of them fail.
* `Cassandra\Connection\Socket::connect()`: the connect retry loop re-invoked `socket_connect()` with the configured host, so every `EINTR`-interrupted attempt triggered a fresh DNS lookup. The loop now connects to the already-resolved numeric address.
* `Cassandra\Value\UDT` / `Cassandra\Value\Tuple`: a serialized value carrying fewer fields than its type declares (for example UDT rows written before an `ALTER TYPE ... ADD`) was decoded by reading past the value's declared length into whatever bytes followed, desyncing the row decoder. Decoding now stops at the declared length and null-fills the remaining trailing fields.
* `Cassandra\Request\Request`: in the untyped value path (a raw PHP value bound without type metadata, i.e. `query(..., autoPrepare: false)` or `Batch::appendQuery()`), an `int` outside the 32-bit range was silently truncated by `pack('N')`, and a `DateTime` was encoded as a formatted string that no temporal column accepts. Both now throw a `Cassandra\Exception\RequestException` pointing at `Value\Bigint`/`Value\Timestamp` or prepared statements, instead of sending a wrong value.
* `Cassandra\Value\Duration`: the string parser silently accepted arbitrary garbage. The value-format patterns were unanchored and consist entirely of optional components, so any input (e.g. `"hello world"`, or a typo like `"5x2d"` where `"2d"` was intended) matched an empty region and produced a zero duration instead of an error. The patterns are now anchored and a match must capture at least one component; invalid strings throw a `Cassandra\Exception\ValueException`.
* `Cassandra\Value\Decimal`: constructing a decimal from a PHP float rounded it to an integer (`new Decimal(1.5)` stored `2`, `new Decimal(0.1)` stored `0`), silently corrupting the written value. Floats are now converted to a plain decimal string preserving their exact (shortest round-trip) value, and non-finite floats (`INF`/`NAN`) are rejected.
* `Cassandra\Value\Decimal::fromBinary()`: the scale field was decoded as an unsigned int instead of the signed int32 the protocol defines. A negative scale (legal for Java `BigDecimal` values) was misread as a huge positive scale, and building the padded value string then exhausted memory. The scale is now sign-extended and negative scales decode correctly (`unscaled * 10^-scale`).
* `Cassandra\Value\Decimal::fromBinary()`: decoding expands the value into a plain decimal string whose length grows with the (signed int32) scale, so a crafted or corrupt `decimal` cell as small as five bytes could force an allocation of up to ~2 GiB and exhaust memory — a decode-side denial-of-service reachable from any query returning a `decimal` column. The absolute scale is now bounded and an out-of-range scale is rejected with a `Cassandra\Exception\ValueException`.
* `Cassandra\Value\Decimal`: constructing a decimal from a numeric string that `is_numeric()` accepts but the varint wire encoding cannot express verbatim — scientific notation (`"1e5"`), a leading `"+"`, surrounding whitespace, or a bare-point form (`".5"`) — was accepted at construction but then threw an "invalid varint" error only later, at `getBinary()` (send) time. Such strings are now normalized to a plain decimal string at construction; plain decimal strings keep their explicit scale (trailing zeros like `"1.50"`) verbatim.
* `Cassandra\Request\Request`: values bound to a prepared statement whose key did not exactly match the server-reported bind marker name — including a mere case difference like `['userId' => …]` against the (lowercase-stored) column `userid` — were silently encoded as `null`, potentially overwriting existing data with a tombstone. The same happened for missing positional values. Named values now match bind marker names case-insensitively, and a value that is genuinely missing for a bind marker throws a `Cassandra\Exception\RequestException` instead of writing `null` (an explicit `null` or `Value\NotSet` is still honoured).
* `Cassandra\Request\Request`: with `names_for_values`, bind names taken from the server's prepared-statement metadata were lowercased before being sent back, which corrupted case-sensitive (quoted) identifiers like `"userId"`. Names originating from server metadata are now sent back unchanged; only user-supplied names (non-prepared `QUERY` path) are still lowercased to match unquoted-identifier semantics.
* `Cassandra\Connection\Socket` / `Cassandra\Connection\Stream`: configured receive timeouts were never enforced on the (default) non-blocking read path — the read select blocked without a timeout, and for streams `stream_set_timeout()` has no effect once the stream is non-blocking. A peer that stayed connected but silent could block a synchronous request forever regardless of `SO_RCVTIMEO` / `timeoutInSeconds`. Reads are now bounded by the configured receive timeout, after which the client re-checks its deadlines.
* `Cassandra\Connection\Socket`: the `usec` component of `SO_RCVTIMEO` / `SO_SNDTIMEO` was ignored, so a sub-second timeout such as `['sec' => 0, 'usec' => 200000]` was rounded up to a full second.
* `Cassandra\Connection\Stream`: `timeoutInSeconds` was truncated to whole seconds for the receive/send timeouts, so `0.5` became `1`.
* `Cassandra\Connection\Socket` / `Cassandra\Connection\Stream`: the send timeout bounded the *whole* payload instead of periods without progress, so writing a large batch or blob over a slow but healthy link failed even while it was making steady progress — effectively capping how much could be written at whatever fitted in the timeout. It is now a stall timeout, reset whenever bytes are written, which is what `SO_SNDTIMEO` means.
* `Cassandra\Connection\Stream` / `Cassandra\Connection\StreamNodeConfig`: configuring `sslOptions` on a host without an explicit `tls://` scheme silently produced a **plaintext** connection, because the ssl context options only take effect on a tls transport. A non-empty `sslOptions` array now enables TLS automatically when the host carries no scheme (an explicit scheme is still respected). The `sslOptions` default changed from an array of verify flags to `[]`; this is behavior-neutral, as the removed defaults match PHP's built-in ssl-context defaults, which continue to apply to any option not set explicitly.
* `Cassandra\Connection\Socket`: a host containing a URL scheme (e.g. `tls://…`, which the socket transport cannot handle) now fails with a clear configuration error pointing at `StreamNodeConfig`, instead of a confusing DNS resolution failure.
* `Cassandra\Response\ResultIterator`: calling `next()` without a preceding `current()` advanced the iteration position but not the row cursor, desynchronizing keys and rows for the rest of the iteration (harmless in a normal `foreach`, which always calls `current()`). `next()` now skips the unread row so position and cursor stay aligned.
* `Cassandra\Value\MapCollection`: a map whose key type decodes to a PHP float or bool (e.g. `map<double, text>`, which is legal CQL) could not be read at all — decoding threw a `Cassandra\Exception\ValueException`. Float keys are now represented as strings (a PHP array would silently truncate them to int) and boolean keys as `1`/`0`.
* `Cassandra\Value\UDT` / `Cassandra\Value\Tuple`: `getBinary()` accessed undeclared fields with an "undefined array key" warning when the supplied value array was missing a field of the type definition. Missing fields are now encoded as `null` cleanly.
* `Cassandra\Request\Prepare::getHash()`: the prepared-statement cache key was built by concatenating query and keyspace without a separator, so distinct `(query, keyspace)` pairs could collide in the cache. The two parts are now delimited.
* `Cassandra\Value\Uuid` / `Cassandra\Value\Timeuuid`: the constructor accepted any string without validation, so a malformed value was silently turned into wrong-length or corrupt binary by `getBinary()` (`pack('H*', …)` coerces non-hex characters to `0`) — a typo'd UUID could be written to the server as 16 bytes of wrong data. The value is now validated at construction — a string that is none of the canonical `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` form (case-insensitive), the compact 32-character undashed hex form, or the raw 16-byte binary form is rejected with a `Cassandra\Exception\ValueException`.
* `Cassandra\Value\Date`: the integer input was documented as "number of days since 1970-01-01", but it is actually the raw `date` wire value — a 32-bit unsigned integer with the epoch centered at `2^31` (so `2^31` is 1970-01-01), matching the [CQL spec](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/types.html#dates). The behavior was already correct; the misleading constructor doc and error message are now corrected.
* `Cassandra\Value\Vector`: fixed two element-framing bugs. `vector<smallint>`/`vector<tinyint>` are variable-length inside vectors ([CASSANDRA-14476](https://issues.apache.org/jira/browse/CASSANDRA-14476)), but `fromStream()` expected no length prefix and misread them; and `getBinary()` wrote the variable-length prefix as a two's-complement varint rather than an unsigned VInt, corrupting elements of 128 bytes or more (e.g. a long `vector<text>`). Both paths now use unsigned-VInt prefixes and agree.
* `Cassandra\Value\Vector`: `getBinary()` serializes exactly `dimensions` elements by positional index, so a value array that was not a `dimensions`-length list was silently mis-encoded — extra elements were dropped without error, and too few or non-`0`-indexed (associative) elements produced "undefined array key" warnings followed by a misleading `ValueFactoryException`. The constructor now rejects a non-list value or an element count that does not match the declared dimensions with a clear `Cassandra\Exception\ValueException`.
* `Cassandra\Request\Request`: when binding named values against prepared-statement metadata, two bind markers reported under the same name collapsed into a single entry, silently sending fewer values than the statement has markers. This is now rejected with a `Cassandra\Exception\RequestException` directing the caller to positional (sequential) binding.
* `Cassandra\Response\Result\SchemaChangeResult` / `Cassandra\Response\Event\SchemaChangeEvent`: schema changes targeting a keyspace (`CREATE`/`ALTER`/`DROP KEYSPACE`) were rejected with "Invalid schema change target", because the `KEYSPACE` target — which carries no `name` field per the protocol spec — was missing from the target dispatch. For results this threw when accessing the schema change data; for events it threw while parsing the response, so a registered event listener could not receive keyspace-level schema change events at all. The event-side `SchemaChangeData::$name` is now nullable, matching the result side, and is `null` for keyspace targets.
* `Cassandra\TypeNameParser`: UDT type strings in the Java class-name format (`org.apache.cassandra.db.marshal.UserType(...)`, received for columns whose type arrives as a custom type, option `0x0000`) were parsed without decoding the hex-encoded UDT name and field names that Cassandra emits in this format. Field names came back as hex strings (`7a6970` instead of `zip`), and — because PHP coerces all-decimal-digit array keys to integers — a field whose hex form happened to contain only digits (e.g. `street` → `737472656574`) made the parser reject the whole type string with a "field keys must be strings" error. Parameter names are now carried as real strings and hex-encoded UDT names and field names are decoded.
* `Cassandra\Response\Response::__toString()`: the re-serialized frame header packed the `ProtocolVersion` enum instance instead of its integer value (emitting a PHP warning and a bogus version byte) and did not set the response direction bit. The version byte is now encoded as `0x80 | version`.
* `Cassandra\Value\Boolean`: a zero-length (empty, non-null) `boolean` cell — legal in Cassandra and distinct from `null` — decoded as `true`. It now decodes as `false`, matching the other drivers.
* `Cassandra\Value\Custom::requiresDefinition()` returned `false` although decoding a custom value requires a `CustomInfo` definition. `ValueFactory::getTypeInfoFromType(Type::CUSTOM)` therefore handed out a bare `SimpleTypeInfo` that later failed inside `Custom::fromBinary()` with a misleading "Invalid type info" error. It now returns `true`, so the factory reports upfront that a custom type needs a definition.
* `Cassandra\Connection`: a failure thrown by an event or warnings listener could be reported to a caller whose request had nothing to do with it. A listener runs from inside the read that took the frame off the wire, so its exception is put aside and raised once the connection has finished with that frame — but only if it gets that far: handling the very frame whose listeners ran can fail on its own (the repreparation limit above all), and the pass then unwound with an exception of its own, leaving the listener's failure behind for the next request that completed normally to raise as a `ConnectionException` naming a listener. What is put aside now belongs to the pass that put it there — `Cassandra\Connection\ListenerRegistry::beginPass()` / `endPass()` — so an aborted pass discards its own and a nested one (a listener issuing a request, a repreparation reading its own answer) can neither see nor clear the failure the outer pass is still going to raise.
* `Cassandra\Response\Result\RowsResult`: the row count was taken from the wire without being checked against the frame body it was read from. A row is at least four bytes per column — a cell's length prefix — so a count past what is left of the body cannot be meant by any well-formed frame, and a result declaring *no* columns has rows of no bytes at all: a sixteen-byte body could announce two billion of them, and `fetchAll()`, `getRowsData()` and `fetchAllColumns()` would each dutifully build an array with an entry per row until memory ran out. Such a result is now refused at construction with a `ResponseException` (`RESPONSE_ROWS_ROW_COUNT_OUT_OF_RANGE`), like the frame length and type nesting limits already in place.
* `Cassandra\Request\Execute` / `Cassandra\Request\Batch`: a prepared statement with a bind marker whose name is a decimal number — a quoted numeric column name, `INSERT INTO t ("0") VALUES (?)` — could never be bound. Values are keyed by marker name on their way to the wire, and PHP turns an array key that is a canonical decimal integer string into an int, so the name arrived as `int(0)` and was rejected with a misleading "sequential array provided while names_for_values=true expects associative array". Names that came from the server's own bind marker metadata are now spelled back out; a caller's own keys are still held to the check, where an int key really does mean a sequential array was passed.
* `Cassandra\Compression\Lz4Decompressor::decompress()`: a frame's content checksum was computed over everything decoded so far rather than over what that frame produced, so an input holding more than one frame failed the second one's checksum with `invalid content checksum`. A back-reference could also reach past the start of its frame into the output of an earlier one. Both are now scoped to the frame being read. Only affects the standalone frame API — the CQL wire path decodes raw blocks and was unaffected.
* `Cassandra\Connection::executeAll()`: each page after the first was requested from the prepared result the call started with rather than from the page just read, so a result metadata id that changed mid-paging (from v5, an `ALTER` while the result set is being walked) was never picked up and the node resent the whole metadata with every remaining page. The page is now chained through, which is what `Cassandra\Request\Execute` accepts a `RowsResult` for; the paging state is still set explicitly so a caller who passed one of their own is unaffected.
* `Cassandra\Response\Result\RowsResult::getRowsData()`: a row that could not be decoded left the reader parked mid-stream while the fetch cursor still said where the caller had got to, so a caller that caught the error and carried on with `fetch()` was handed the middle of a row. The reader position is now restored however the call ends.
* `Cassandra\Value\Decimal`: a value in scientific notation was expanded into the plain decimal string it stands for without any bound on the exponent, so `"1e50000000"` — three bytes of `is_numeric()`-approved input — allocated a fifty-megabyte string and a larger exponent exhausted memory. The exponent is now bounded at the same magnitude as a decoded scale, raising a `ValueException` (`VALUE_DECIMAL_EXPONENT_OUT_OF_RANGE`) beyond it.
* `Cassandra\Response\StreamReader::readLongString()`: a negative length came back as the empty string, leaving the bytes it announced in the stream to be read as whatever followed. A `[long string]` has no null form — that is what `[bytes]` is for — so a negative length is now refused with a `ResponseException` (`RESPONSE_SR_INVALID_LONG_STRING_LENGTH`).
* `Cassandra\Connection\ResponseReader`: the "decompressed frame length does not match expected length" exception carried the raw `unpack()` array in its `expected_length` context instead of the length itself.
* `Cassandra\Value\MapCollection`: a `map<boolean, …>` could not be encoded at all, so inserting or updating one always failed with `Invalid boolean value; expected bool`. A PHP array key is an int or a string and nothing else, so a boolean key is already `1` or `0` by the time the driver sees it — PHP folds it on assignment, and `fromStream()` spells the same coercion out for the keys it decodes — but `getBinary()` handed that int straight to `Cassandra\Value\Boolean`, which takes a bool and refuses everything else. The coercion is now undone on the way out, so a map built by hand and one read off the wire both encode; a value read from such a column can therefore be written back, which it could not before.
* `Cassandra\Response\Result\RowsResult::getIterator()`: an iterator taken after some rows had already been fetched stopped that many rows early, handing back `false` for each of the rows it skipped rather than the rows its reader was in fact positioned on. The iterator works on a clone, which carries the fetch cursor as well as the reader, and only the reader was being put back to the first row. `foreach` was unaffected — it calls `rewind()` before the first element, which puts the two back in step — so this only showed on an iterator driven by hand.
* `Cassandra\Value\Varint`: an integer string was kept verbatim rather than reduced to the value it names, so `'007'` stayed `'007'` and `'0000000000000000000'` stayed nineteen zeros where the same value read back from the node was `'0'` — the wire encoding has no way to show a leading zero. `getValue()` and `asString()` now report the canonical form. The int/string cutoff was also a digit count that stayed safely below the real bound, which gave up the whole top of the range: `asInt()` refused every value from 10^18 to `PHP_INT_MAX` — and `VarintEncodeOption::AS_INT` threw for them — although the same value arriving from a node came back as an int. It is now measured against `PHP_INT_MAX`/`PHP_INT_MIN` themselves, on 32-bit builds as well as 64-bit ones. The encoded bytes are unchanged throughout.
* `Cassandra\Value\Decimal`: leading zeros of the integer part were kept verbatim, so `'007.5'` reached the application through `getValue()` as `'007.5'` while the node returned `'7.5'`. They are now dropped. The fraction is still kept exactly as given — that is what carries the scale, so `'1.50'` remains `'1.50'`.
* `Cassandra\Compression\Lz4Decompressor::decompress()`: a legacy-format frame (magic `0x184C2102`) carrying more than one block was refused with "invalid magic number". The format has neither a frame length nor an end mark — its blocks simply follow one another until the input runs out or another frame begins — and only the first was read, after which the second block's size field was taken for a magic number. The whole sequence is now read, and a frame that ends because another begins leaves that magic number for the next frame.
* `Cassandra\Connection\Stream`: a `stream_select()` that failed for a real reason was retried forever when the transport was configured without a stall window (`StreamNodeConfig(timeoutInSeconds: 0)` or less), spinning at full CPU on a connection that could not recover. PHP reports an interrupted select exactly as it reports a failed one, so a failure is retried rather than taken as fatal — but the elapsed-time test that ends those retries can never fire against an infinite window. Consecutive failures are now counted as well, and a genuine failure is reported once they run out. The socket transport was never affected: `socket_select()` reports `EINTR` through an errno, so it retries only what really is an interruption.
* `Cassandra\Request\Execute`: an `EXECUTE` re-sent after an `UNPREPARED` carried the values encoded for the statement the node had just forgotten. A repreparation is exactly the case where the bind marker types may have moved — an `ALTER`, or a table dropped and created again, is one of the reasons a node stops recognising a statement id — but the replacement request was built from the refused request's *encoded* values, which `encodeQueryValuesForBindMarkerTypes()` passes straight through. So the new statement id went out with the old statement's encoding: rejected by the node where the widths differ (`int` → `bigint`), and silently wrong where they do not (an `int` bound to a `text` column arrived as the four bytes of its int32 form). The values the caller passed are now kept alongside the encoded ones and re-encoded against the metadata the repreparation returned, which is what `Cassandra\Request\Batch` has always done — and which also makes a renamed marker report a missing bind value instead of binding to whatever sits at its old position. `Cassandra\Request\Execute::getUnencodedValues()` is the new accessor; `getValues()` is unchanged and still returns what goes on the wire.
* `Cassandra\Connection\PreparedResultCache`: the copy of the `PREPARE` an entry keeps was replaced with the caller's own object again whenever a *prepare* was served from the cache asynchronously (`prepareAsync()`, or `asyncRequest()` with a `Prepare`). A cache hit on that path is handled like any other answer, and handling a `PREPARE` answer records the request that produced it — which undid the copy this list already describes above, leaving the entry free to follow that request's later sends and to name a keyspace other than the one it is filed under. The synchronous path was never affected: it returns the entry without handling it. A cached result now keeps the copy it was stored with.
* `Cassandra\Value\Vector`: the value-encode config did not reach a vector element that is itself a container, so a `timestamp` nested in, say, a `vector<list<timestamp>, n>` was reported in the default encoding however `ValueEncodeConfig` was set. A scalar element was unaffected — the config is applied to it after decoding — but a collection decodes its own children inside `fromStream()` and is not a `ValueWithMultipleEncodings`, so nothing downstream put the config back. The config is now handed to the element's decoder as well.
* `Cassandra\Request\Query`: a case-sensitive bind marker was lost after a dollar-quoted string literal. The scan that collects `:"Quoted"` marker names skips string literals, quoted identifiers and comments so that a colon inside one is not mistaken for a marker — but it did not know CQL's `$$…$$` form, whose whole purpose is to carry apostrophes unescaped. The first of those apostrophes was taken for the start of an ordinary literal and the scan ran to the end of the query looking for its partner, so every quoted marker after it was missed and went out lowercased: `INSERT INTO t (a, b) VALUES ($$it's fine$$, :"MyCol")` sent `mycol` and the node answered "Undefined name". A `:"…"` *inside* such a literal was correspondingly taken for a marker. Both are now handled.
* `Cassandra\Value\ListCollection`, `SetCollection` and `MapCollection`: the element count of a collection read through the value-object path was bounded by what was left of the frame rather than by the length its own cell declares. A cell declaring eight bytes could therefore announce millions of entries and have the driver build the array for them out of the bytes of the cells that follow, with `Cassandra\Response\StreamReader::resyncAfterValue()` reporting the over-read only afterwards — once the memory had already been asked for. The tighter bound `StreamReader::readCollectionValues()` has always applied to a row's own list and set cells is now applied here too, which covers every map and any list or set nested in a tuple or UDT.
* `Cassandra\Value\Time::asDateTime()` now returns a `DateTimeImmutable` anchored at UTC, as `Date::asDateTime()` and `Timestamp::asDateTime()` already did. It used to take the ambient `date_default_timezone_set()`, so the three temporal types handed back objects whose offsets disagreed for values that mean the same instant of the day. See Breaking Changes.
* `Cassandra\Connection`: a frame that was consumed whole and then refused — an unknown result kind, an unknown error code, a body that could not be decoded, a decompression failure — gave the stream id it named back to the pool even when that id belonged to a synchronous wait that was still running. A sync request registers no statement, so its id is held by the wait itself and nobody else can tell whether that wait is the one unwinding; the read that refuses the frame need not be its own, an event or warnings listener issuing a request of its own reading from inside it. The id was then free to be handed to a later request, whose answer the waiting loop matched on the number and returned as its own result. The wait was also told nothing, so it ran out its whole budget and reported a `RequestTimeoutException` for a request the node had in fact answered. The failure is now put aside for the wait it belongs to, exactly as an answer already was: the owner reports the real exception at once and gives its id back as it unwinds. A listener that swallows what it catches was the only way to reach the second half, but the id went back into circulation either way.
* `Cassandra\Response\Result\RowsResult::fetchAllColumns()` now rejects a column index the result set does not have (`RESPONSE_ROWS_INVALID_COLUMN_INDEX`) even when the cursor is already at the end. The index was checked only by the `fetchColumn()` calls it makes, which a consumed cursor never reaches, so naming a column that does not exist came back as an empty array — indistinguishable from a result that really had no rows left. `fetchAllKeyPairs()` already checked up front.
* `Cassandra\Value\Vector`: a vector cell that stopped short of its declared dimensions was read on into the cells that followed it. A vector carries no element count — the dimensions come from its type — so nothing bounded the read by the length the cell declares, and `Cassandra\Response\StreamReader::resyncAfterValue()` reported it afterwards as a value that overran its cell: true, but saying nothing about the vector it was, and only once the following cells had been consumed. Such a value is now refused where it runs out, with a `Cassandra\Exception\ValueException` (`VALUE_VECTOR_TRUNCATED_VALUE`) naming the dimension the data ended at.
* `Cassandra\Value\Timestamp`: a string that named no UTC offset was read in the ambient `date_default_timezone_set()` zone, so the same literal meant a different instant on every machine that sent it — `'2024-01-01 12:00:00'` was three different timestamps under `UTC`, `America/New_York` and `Asia/Tokyo`. `getValue()` spelled the value back out in UTC regardless, and `Date` and `Time` were anchored at UTC on both sides, so `timestamp` was the one type whose meaning depended on how the process happened to be configured. Such a string is now read as UTC. A string that does carry an offset, or `Z`, is unaffected — the zone was only ever the fallback — as are the `int` and `DateTimeInterface` forms, which name an absolute instant already.
* `Cassandra\Connection`: on the v5 framing, a payload the transport could not decompress left the connection in use even though the envelope stream had lost bytes. `Cassandra\Connection\FrameCodec` verifies the payload CRC32 and consumes the whole outer frame before it decompresses, so a payload it then refuses was a slice of the stream `Cassandra\Connection\ResponseReader` walks — the same predicament a refused response header leaves, and one every later envelope would be assembled through. It was treated as the other kind of reader failure instead, the kind that costs one request and leaves the stream in step. Such a failure now drops the connection, as a refused header already did; the next request opens a fresh one. Reachable only from a peer whose payload passed its own checksum and then would not decompress.
* `Cassandra\Value\Inet` now refuses an address it cannot encode where it is named (`VALUE_INET_INVALID_ADDRESS`) instead of at `getBinary()` — which for a bound value is several calls later, and for a collection element is under a failure that names the collection. See Breaking Changes.

### Performance
* `Cassandra\Connection\NodeImplementation`: while a large response body accumulated across partial reads, the read buffer was rebuilt (fully copied) on every read; it is now appended to in place when nothing has been consumed yet, avoiding quadratic copying.
* Response and value dispatch maps (`Cassandra\Response\Response`, `Result`, `Error`, `Event`, `Cassandra\ValueFactory`, `Cassandra\TypeNameParser`) are now lazily cached instead of being rebuilt on every call.
* `Cassandra\Response\StreamReader::readValue()`: scalar, list and set cells are now decoded directly without allocating an intermediate `Value` object per cell.
* `Cassandra\StringMath\DecimalCalculator\Native`: varint conversion is roughly seven to seventeen times faster, the wider the value the larger the gain. The pure-PHP calculator worked a digit at a time, paying an `ord()` and a `chr()` per digit per byte of the value; it now works a whole chunk of digits at a time in a single PHP int — sixteen of them where `PHP_INT_SIZE` says the platform can carry them, six on a 32-bit build (where the gain is six to eight times), each being the widest chunk whose intermediates all stay inside a signed platform integer. Adding a byte also stops as soon as its carry is spent instead of rewriting the whole number. Conversion remains quadratic in the length of the value, which is what `Cassandra\Value\Varint::MAX_MAGNITUDE_DIGITS` bounds. Builds with `gmp` or `bcmath` are unaffected — they never reach this code.
* `Cassandra\Request\Query`: the query string is no longer scanned for quoted bind marker names when the result cannot be consulted, i.e. unless the request actually sends names for its values.
* `Cassandra\Value\ValueComparator`: comparing two collections or maps no longer builds a throwaway array holding one copy of the element type per element.

The fake server gained an `unprepared-execute-retyped` mode, which refuses the first `EXECUTE` and then hands out a statement whose marker is a `bigint` where the refused one's was an `int`.

* `TransportReadDeadlineTest`'s "the deadline ended this read, not the stall window" assertions share one named bound with enough headroom to survive a loaded machine. The tightest of them asserted that a 0.3s deadline finished within 3s against a 15s stall window, which failed under CPU contention while telling nothing apart that 10s does not.

The fake server gained an `event-then-bad-result` mode, which pushes an event and then answers the query it interrupted with a frame the client cannot decode, so the read that refuses it is the listener's own nested one.
* `EmptyValueConformanceTest` now pins the `allowsEmpty()`/`isEmptyValueMeaningless()` matrix per type rather than only holding the two decoders to whatever each type declares. Self-consistency was all the existing tests could see, so a wrong declaration passed them — which is how the docblock on `StreamReader::emptyValue()` came to name `date`, `time`, `smallint` and `tinyint` among the types that report an empty value as null when their serializers demand an exact width and they refuse one.
* The timing tests no longer sleep with a bare `usleep()`. PHP's `usleep()` does not resume after a signal — it returns early and says nothing about it — and a test process that starts and reaps a fake server per test takes `SIGCHLD` routinely, so `usleep(1_000_000)` was observed returning after 0.33s. Every one of those sleeps exists to put a deadline in the past before the driver is asked what it made of it, so a short one did not slow the test down but made it assert the opposite of what it means: `testAPolledStatementStillRunsOutOfTime` failed intermittently because a 0.5s budget genuinely had not run out yet and the driver was right not to enforce it. `AbstractUnitTestCase::sleepAtLeast()` sleeps until the wall clock says so, however often it is interrupted.
* `RequestTimeoutTest`: three further tests no longer depend on the client process not being starved for seconds. The one that pins a request timeout firing under a much longer stall window asserted it within 4s of a 0.5s budget, which measures the machine rather than the 15s window it is about; the one that pins a statement timing out while another survives had the server hold the slow answer 4s against a 1s budget, so a long enough stall let that answer arrive inside the wait — where it is rightly handed back rather than reported as a timeout; and the two that pin the orphaned-stream limit relied on two statements sent microseconds apart going overdue in the same pass of the wait, which decides whether the caller is told the connection was replaced or that one request timed out.
* `RequestTimeoutTest::testAStatementNotBeingWaitedOnStillRunsOutOfTimeDuringAWait` no longer measures a park time against the wall clock, which made it fail intermittently on a loaded machine: the driver hands the read a deadline, but when the process is scheduled to come back from it is the operating system's business, and the assertion had no slack for that. It now puts two statements with budgets 1.5s apart outside the waited set and compares when they were parked *against each other* — held to their own budgets they are given up on an interval apart, whereas a wait bounded by the waited set alone notices neither until it ends and parks both in the same pass. A stall shifts both equally, so it cannot fail the check; reintroducing the bug collapses the interval to microseconds.

## v1.1.0

This release introduces the ability to override the default pool of allowed protocol versions (v5, v4, v3) via the new `allowedProtocolVersions` property in `ConnectionOptions`. This is a low-level feature intended for advanced use cases and should not be used by most users. The default behavior, which attempts to negotiate the highest supported version (v5 > v4 > v3), is recommended for the majority of situations.

All breaking changes affect low-level API only, which is unlikely to be used by most users.

### Breaking Changes
* Cassandra\Protocol\Header: type of `$version` changed from `int` to `Cassandra\Protocol\ProtocolVersion`
* These methods now expect for `$version` a value of type `Cassandra\Protocol\ProtocolVersion` instead of `int`:
    * `Cassandra\Connection\ResponseReader::readResponse()`
    * `Cassandra\Request\Request::__construct()`
    * `Cassandra\Request\Request::setVersion()`
* Exception context: type of `protocol_version` changed from `int` to `string`

### Changed
* Cassandra\Connection: method `getVersion()` is now deprecated, use `getProtocolVersion()` instead
* Cassandra\Protocol\Frame: method `getVersion()` is now deprecated, use `getProtocolVersion()` instead
* Cassandra\Request\Request: method `getVersion()` is now deprecated, use `getProtocolVersion()` instead
* Cassandra\Response\Response: method `getVersion()` is now deprecated, use `getProtocolVersion()` instead
* Changed visibility of some properties and methods from `protected` to `private` to clarify public api

### Added
* Added enum `Cassandra\Protocol\ProtocolVersion`
* Cassandra\Connection\ConnectionOptions: added property `allowedProtocolVersions` (array of enum `Cassandra\Protocol\ProtocolVersion` )
* Cassandra\Connection: added method `getProtocolVersion(): ProtocolVersion`
* Cassandra\Protocol\Frame: added method `getProtocolVersion(): ProtocolVersion`
* Cassandra\Request\Request: added method `getProtocolVersion(): ProtocolVersion`
* Cassandra\Response\Response: added method `getProtocolVersion(): ProtocolVersion`

## v1.0.0 "Prism" 🔷🌈

This release brings major improvements across the library.
In contrast to previous releases, it includes some breaking API changes. These were necessary to introduce more exciting features (including full support for the `Vector` data type 🤖) and to enhance and fix existing ones.

Upcoming 1.x releases will focus on stability and performance while keeping the API stable.

* Support for configuring value encoding for data types with multiple encodings
